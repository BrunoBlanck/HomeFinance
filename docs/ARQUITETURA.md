# Arquitetura — HomeFinance

Decisões fundamentadas na pesquisa de 09/2026 (`docs/PESQUISA.md`).

## Visão geral

```
┌─────────────────┐        HTTPS/JSON        ┌──────────────────────────────┐
│  Frontend React │ ───────────────────────▶ │  Backend Go (API REST)       │
│  (Vite 8, SPA)  │ ◀─────────────────────── │  domínios + platform         │
└─────────────────┘   contrato OpenAPI 3.1   └──────────────┬───────────────┘
                                                            │ GORM v2 (ADR-008)
                                             ┌──────────────▼───────────────┐
                                             │  Qualquer banco SQL          │
                                             │  Postgres│MySQL│SQLite│MSSQL │
```

## Backend (Go 1.26)

### Layout por domínio (guia oficial go.dev/doc/modules/layout — ver ADR-004)

```
backend/
  cmd/api/main.go              ← composição: config → db → domínios → server
  api/openapi.yaml             ← contrato OpenAPI 3.1 (fonte de verdade — ADR-006)
  internal/
    household/  user/  account/  category/  transaction/  bill/  budget/
      │   Cada domínio contém: types.go (entidades e erros), service.go (regra
      │   de negócio), repository.go (INTERFACE), handler.go (HTTP), *_test.go
    auth/                      ← JWT access, refresh opaco com rotação, Argon2id,
      │                          verificação de e-mail e OTP de 6 dígitos (ADR-009)
    platform/
      config/                  ← env fail-fast (caarlos0/env); único os.Getenv
      httpserver/              ← router (ServeMux), middlewares: auth, rate limit
      │                          (x/time/rate), headers, recover, slog
      mailer/                  ← interface Mailer: console (dev) | SMTP (prod)
      storage/                 ← conexão GORM por DB_DRIVER + AutoMigrate no boot
        gormstore/             ← implementações dos repositórios (ADR-008)
```

**Regra de dependência:** os pacotes de domínio são o núcleo e não importam `platform`; `platform/storage/*` implementa as interfaces dos domínios; `cmd/api` liga tudo. Handler → service → repository (interface) — nenhuma camada pula a de baixo.

- Roteamento: `net/http.ServeMux` nativo (`mux.HandleFunc("GET /api/v1/bills/{id}", ...)`). Sem framework web.
- Injeção de dependência manual por construtores. Sem DI framework, sem globals.
- Erros embrulhados com contexto (`fmt.Errorf("saving bill: %w", err)`); erros de domínio são valores exportados que o handler traduz para HTTP.
- `context.Context` em toda a cadeia; queries sempre `...Context`.
- Validação de entrada com go-playground/validator v10 na borda.

## API — convenções

- Contrato **OpenAPI 3.1 spec-first** (`backend/api/openapi.yaml`): a spec é editada primeiro; oapi-codegen gera tipos/stubs Go e os tipos TypeScript do frontend derivam da mesma spec. Divergência entre código e spec é bug.
- Base: `/api/v1`. Recursos no plural, kebab-case: `/api/v1/recurring-bills`.
- JSON `camelCase`. Datas ISO 8601 UTC. Dinheiro em **centavos (inteiro)**: `{"amountCents": 12990}`.
- Paginação por cursor: `?limit=50&cursor=...` → `{"items": [...], "nextCursor": "..."}`.
- Erro padrão único:

```json
{ "error": { "code": "VALIDATION_FAILED", "message": "mensagem segura em pt-BR", "fields": {"amountCents": "deve ser positivo"} } }
```

- Códigos: 400 validação · 401 não autenticado · 403 sem permissão · **404 para recurso inexistente OU de outra casa** · 409 conflito · 422 regra de negócio · 429 rate limit · 500 genérico.

## Frontend (React 19.2 + Vite 8)

### Estrutura feature-based (bulletproof-react — ver ADR-007)

```
frontend/src/
  app/            ← TanStack Router (árvore de rotas), providers, config
  features/       ← auth/ dashboard/ transactions/ bills/ budgets/ reports/
      │   Cada feature: api/ (queryOptions + mutations), components/, hooks/,
      │   schemas/ (Zod 4), types/ — só as pastas necessárias
  components/     ← design system próprio (Button, Input, Table, Modal…)
    icons/        ← ícones SVG únicos do projeto
  styles/         ← tokens.css (OKLCH), reset, tipografia, @layer
  lib/  hooks/    ← utilidades compartilhadas (api client, formatação pt-BR)
```

- **Arquitetura unidirecional**: `lib/components` → `features` → `app`. **Imports entre features são proibidos** (lint) e **barrel files são proibidos** (tree-shaking).
- Rotas e **search params tipados** com TanStack Router; filtros vivem na URL (`/transacoes?mes=2026-09`) validados com Zod.
- Estado do servidor: TanStack Query v5 — `queryOptions` co-locados em `features/*/api/`, `useSuspenseQuery` + ErrorBoundary por rota, `useOptimistic`/`useMutation` para ações rápidas (ex.: marcar conta como paga).
- Formulários: react-hook-form + Zod 4 (schema compartilhado entre form, search params e contrato da API).
- Estilo: CSS Modules + tokens; CSS moderno baseline (nesting, `:has()`, container queries, `@layer`, `color-mix` em OKLCH). Transições com a View Transitions API do navegador (nunca a experimental do React), respeitando `prefers-reduced-motion`.
- Lint/format: **Biome** + typescript-eslint mínimo (regras type-aware) + react-hooks; TS `strict` + `noUncheckedIndexedAccess`.

## Domínio (modelo conceitual)

- **Household** (casa) — unidade de isolamento de dados. Todo dado pertence a uma casa.
- **User** — pertence a uma ou mais casas com papel (`owner`, `member`).
- **Account** — conta (carteira, banco, cartão) de onde sai/entra dinheiro.
- **Category** — categoria de receita/despesa, hierárquica (ex.: Casa → Energia).
- **Transaction** — lançamento (receita/despesa/transferência) em centavos.
- **RecurringBill** — conta recorrente (aluguel, luz) que gera transações previstas.
- **Budget** — orçamento por categoria/mês.

## Decisões de arquitetura (ADRs)

### ADR-001 — Roteador nativo em vez de framework web
- **Decisão:** `net/http` puro (ServeMux 1.22+); middlewares como `func(http.Handler) http.Handler`. chi só se a árvore de middlewares crescer (100% compatível).
- **Consequências:** zero dependências no caminho HTTP; menos superfície de ataque.

### ADR-002 — `database/sql` + sqlx + repositórios por interface — ❌ **SUPERADO pelo ADR-008 (09/09/2026)**
- **Contexto:** requisito de aceitar qualquer banco SQL, incluindo SQL Server — o que **eliminou sqlc** (sem suporte a MSSQL).
- **Decisão original:** sem ORM; `database/sql` com **sqlx**; migrações com goose.
- **Status:** **SUPERADO.** O usuário decidiu em 09/09/2026 adotar GORM em todo o projeto — ver **ADR-008**. sqlx e goose **não entram no código**. O que sobrevive desta decisão: repositórios continuam sendo interfaces nos domínios, com a implementação isolada em `platform/storage`.

### ADR-003 — Dinheiro como inteiro em centavos
- **Decisão:** `int64` centavos no backend e `BIGINT` no banco; `amountCents` no JSON; formatação só na borda do frontend. Float proibido.

### ADR-004 — Layout por domínio, não por camada técnica (09/2026)
- **Contexto:** golang-standards/project-layout não é oficial; o guia oficial e a prática atual favorecem pacotes por domínio (`internal/transaction`) em vez de camadas horizontais (`internal/handlers` + `internal/services`).
- **Decisão:** um pacote por domínio contendo handler, service, tipos e a interface do repositório; infraestrutura compartilhada em `internal/platform/`.
- **Consequências:** coesão alta (tudo de "transação" num lugar), features fáceis de achar; a disciplina de camadas passa a ser por arquivo/da interface, verificada em revisão.

### ADR-005 — Bibliotecas padrão de fato (09/2026)
- **Decisão:** `golang-jwt/jwt/v5` (⚠️ dgrijalva/jwt-go abandonada — proibida), go-playground/validator v10, `log/slog`, caarlos0/env, `golang.org/x/time/rate`. ~~goose v3~~ **removido pelo ADR-008** — a evolução de schema é o `AutoMigrate` do GORM.
- **Consequências:** todas mantidas ativamente, mínimo de dependências transitivas; migração aplicada no boot, sem CLI no deploy.

### ADR-006 — OpenAPI 3.1 spec-first com oapi-codegen (09/2026)
- **Contexto:** spec escrita depois do código (ou swaggo por anotações) é legado; contrato tipado ponta a ponta reduz erro humano — ganho direto de segurança de entrada.
- **Decisão:** `backend/api/openapi.yaml` é a fonte de verdade; oapi-codegen gera server stubs/tipos Go sobre stdlib; o frontend gera seus tipos TS da mesma spec.
- **Consequências:** frontend e backend nunca divergem silenciosamente; a spec é revisável no PR.

### ADR-007 — Frontend: TanStack Router + Query, RHF + Zod 4, Biome (09/2026)
- **Contexto:** para SPA client-heavy, TanStack Router entrega tipagem ponta a ponta (rotas + search params) que React Router v7 só tem em framework mode/SSR; Biome unifica lint+format com 10–25× a velocidade.
- **Decisão:** TanStack Router + Query v5; react-hook-form + Zod 4; Biome + typescript-eslint mínimo type-aware; Vitest 4 com Browser Mode para componentes.
- **Consequências:** filtros na URL tipados e validados; um schema Zod serve form, URL e contrato; toolchain rápida.

### ADR-008 — GORM como camada de persistência e AutoMigrate como evolução de schema (09/09/2026)
- **Contexto:** decisão direta do usuário, que reverte o ADR-002. O requisito multi-banco continua de pé: GORM tem drivers oficiais para os quatro dialetos, então nada se perde em portabilidade.
- **Decisão:** **GORM v2** (`gorm.io/gorm`) é a única camada de acesso a dados do projeto. Drivers: `gorm.io/driver/postgres`, `gorm.io/driver/mysql`, `gorm.io/driver/sqlserver` e **`github.com/glebarez/sqlite`** para SQLite (baseado em `modernc.org/sqlite`, **puro Go, sem CGo** — mantém o build reproduzível e cross-compilável). **SQLite é o banco de desenvolvimento.** O schema é declarado nas structs Go com tags `gorm:"..."` e evoluído por **`AutoMigrate` no boot**; goose sai do projeto.
- **Limite conhecido e aceito:** `AutoMigrate` cria tabelas, colunas, índices e constraints que faltam, mas **nunca remove nem renomeia** coluna, e não altera tipo de forma destrutiva. Qualquer mudança destrutiva futura exige migração manual explícita, registrada em ADR próprio.
- **Fronteiras que continuam valendo:** o repositório é uma **interface** declarada no pacote do domínio; GORM vive apenas na implementação em `platform/storage/gormstore`. **`*gorm.DB` nunca aparece em service ou handler.** BOLA continua sendo filtro por `household_id` em toda query, e dinheiro continua `int64` em centavos.
- **Consequências:** menos SQL à mão e schema evoluindo junto com o código; em troca, o SQL gerado passa a ser responsabilidade do ORM — a revisão de segurança precisa conferir que nenhuma query usa `Raw`/`Exec` com interpolação de entrada do usuário.

### ADR-009 — Verificação de e-mail obrigatória com código de 6 dígitos (09/09/2026)
- **Contexto:** decisão do usuário — nenhuma conta existe sem prova de posse do e-mail, e a recuperação de senha usa a mesma mecânica.
- **Decisão:** o registro cria o usuário como **não verificado**; o login só é liberado após a confirmação de um código numérico de 6 dígitos enviado por e-mail. O mesmo mecanismo serve "esqueci minha senha". O envio passa por uma **interface `Mailer`**: implementação de console/log em desenvolvimento (o código aparece no `slog`, nenhum e-mail sai da máquina) e SMTP em produção, escolhida por env — mesma estratégia do driver de banco.
- **Consequências:** um único fluxo de OTP atende cadastro e recuperação; regras normativas (geração com `crypto/rand`, guarda só do hash HMAC, uso único, expiração, limite de tentativas, resposta que não revela existência do e-mail) na seção 1.1 de `docs/SEGURANCA.md`.

### ADR-010 — Toolchain Go 1.26 resolvido pelo `GOTOOLCHAIN=auto` (09/09/2026)
- **Contexto:** a documentação declarava "Go 1.27", mas o `go` instalado na máquina é **go1.24.1**. As versões atuais de `golang.org/x/crypto`, `x/time`, `x/sys` e `x/text` declaram `go 1.26.0` nos seus `go.mod`, e desde o Go 1.21 essa diretiva é requisito duro.
- **Verificação feita (não é hipótese):** com `GOTOOLCHAIN=auto` (o padrão), o Go **baixa e usa o toolchain 1.26.0 automaticamente**. Confirmado neste ambiente: `go build ./...` e `CGO_ENABLED=0 go build ./...` passam com as versões mais recentes de todas as dependências, e `go version` dentro do módulo reporta `go1.26.0`.
- **Decisão:** `backend/go.mod` declara `go 1.26.0`. **Não** fixamos tetos de versão em `x/crypto`, `x/time`, `x/sys` ou `x/text` — a hipótese de que seria preciso rebaixá-los foi levantada no planejamento e **refutada empiricamente**. Fica registrada a única consequência operacional: uma máquina nova precisa de rede na primeira build para o Go buscar o toolchain, ou de um Go ≥1.26 já instalado.
- **Consequências:** dependências ficam em dia (menos superfície de CVE, que é o motivo de a regra das duas últimas majors existir) e o build é reproduzível. Se algum dia for necessário travar em toolchain local, basta `GOTOOLCHAIN=local` — e aí os pins voltam a ser discutidos num ADR próprio.

### ADR-011 — OpenAPI 3.1 versionado com handlers manuais nesta fundação (adiamento controlado do oapi-codegen) (09/09/2026)
- **Contexto:** o ADR-006 estabelece spec-first com oapi-codegen. Na fundação de autenticação, os handlers têm comportamento deliberadamente **não uniforme e crítico à segurança** — cookies com prefixo condicional, respostas propositalmente idênticas para não vazar existência de conta, normalização do tempo de resposta, limpeza de cookies no caminho de erro. É código para ser lido e revisado linha a linha.
- **Decisão:** o ADR-006 continua valendo quanto ao **contrato**: `backend/api/openapi.yaml` é escrito antes dos handlers e versionado como fonte de verdade. Fica **adiada apenas a geração de código**. Para o adiamento não virar dívida invisível, `cmd/api/routes_test.go` valida no `go test` que o conjunto de `(método, path)` da spec é exatamente o da tabela de rotas — divergência quebra o build.
- **Gatilho de reversão (explícito):** ao ultrapassar 25 endpoints, **ou** na primeira geração de tipos TypeScript do frontend a partir da spec, o wiring do oapi-codegen entra e este ADR é encerrado.
- **Consequências:** frontend e backend já compartilham o contrato; o custo é que a aderência de *schemas* (não só de rotas) fica por revisão humana até o gerador entrar.

### ADR-012 — Ciclo de vida da conta: casa criada na verificação e OTP ancorado no e-mail (09/09/2026) — ⚠️ **parcialmente revisto pelo ADR-014**
- **Contexto:** o ADR-009 exige verificação obrigatória por código de 6 dígitos e a mesma mecânica para recuperação de senha. Faltava definir quando a `household` nasce e o que o OTP referencia.
- **Decisão:** o registro cria **apenas** o usuário não verificado. A `household` (`"Casa de {primeiro nome}"`) e a `membership` de `owner` são criadas na **verificação do e-mail**, na mesma transação que grava `email_verified_at`. A criação é idempotente (`EnsureDefault`) e também roda no login como auto-reparo, garantindo o invariante **"todo usuário verificado tem ao menos uma casa"** — do qual depende a claim `hid` do access token. `verification_codes` é ancorado em **`email + purpose`**, com `user_id` anulável, e **nenhuma linha-isca** é criada para e-mail inexistente. ~~Registro sobre e-mail existente e **não verificado** sobrescreve nome e hash pendentes e reemite o código.~~ — **revisto pelo ADR-014 (09/09/2026):** sobrescrever credenciais pendentes é justamente o que abre o *pre-hijacking*; hoje cada cadastro abre uma **tentativa própria** e a ativação usa as credenciais da tentativa dona do código.
- **Consequências:** spam de registro não gera casas órfãs; a validação de código tem a **mesma forma de consulta** exista ou não a conta, o que sustenta as respostas idênticas exigidas pela §1.1 de `docs/SEGURANCA.md`; em troca, o fluxo de verificação passa a ser transacional e exige `UnitOfWork`.

### ADR-013 — Sessão em cookie `__Host-`, CSRF por `Origin` e ausência de FK física (09/09/2026)
- **Contexto:** três escolhas estruturais da camada de borda e de persistência que valem para todo o resto do projeto.
- **Decisão:** **(a)** access e refresh viajam em cookies `HttpOnly; Secure; SameSite=Strict; Path=/`, com prefixo `__Host-` sempre que `COOKIE_SECURE=true`, protegendo contra sobrescrita a partir de subdomínio comprometido (*session fixation*); **(b)** a defesa de CSRF é `SameSite=Strict` **mais** checagem de `Origin`/`Sec-Fetch-Site` contra a allowlist do CORS em todo método não seguro — sem token double-submit e sem dependência nova, já que o backend não serve formulário HTML; **(c)** o schema **não tem chave estrangeira física** (`DisableForeignKeyConstraintWhenMigrating: true`): a integridade é garantida em Go, dentro de transação, com índice em toda coluna de referência.
- **Por que (c), em detalhe:** o `AutoMigrate` só gera FK a partir de campos de associação, e associação em struct traz o *auto-save* do GORM (risco de upsert acidental do pai); `ON DELETE RESTRICT` não é T-SQL válido e quebraria o `AutoMigrate` no SQL Server; e o MSSQL rejeita múltiplos caminhos de cascade, o que estouraria já na Fase 4 (`transactions` → `households` e → `accounts` → `households`).
- **Consequências:** o `AutoMigrate` fica portátil nos quatro dialetos sem exceções. O preço é que linha órfã por bug de código **não é barrada pelo banco**: toda escrita multi-tabela **tem** que passar por `UnitOfWork`, e isso vira item permanente de revisão de segurança.

### ADR-014 — Tentativa de cadastro com `registrationToken`: o código pertence a quem o pediu (09/09/2026)
- **Contexto:** o modelo do ADR-012 guardava o cadastro pendente como **uma linha em `users`**, e o código de 6 dígitos ficava ancorado em `email + purpose`. Isso deixa o código que chega à caixa de entrada **desligado de quem escolheu a senha**, e abre *pre-hijacking* de conta (Sudhodanan & Paverd, USENIX Security 2022). Nenhuma política de sobrescrita fecha o buraco: com *último escreve vence*, o atacante cadastra por último e a vítima ativa a senha dele ao usar o próprio código; com *primeiro escreve vence*, o cadastro da vítima vira no-op e dá no mesmo; bloquear e-mail com cadastro pendente vira **negação permanente de cadastro** por procuração.
- **Decisão:** cada `POST /auth/register` abre a sua própria **tentativa de cadastro** (tabela `registration_attempts`), que carrega as credenciais daquele pedido, o HMAC do seu código e o SHA-256 de um **`registrationToken`** opaco de 256 bits (`crypto/rand`, guardado só como hash, devolvido no corpo do 202). `POST /auth/verify-email` passa a exigir o token junto do código, e a busca é **escopada pelo token**: código de outra tentativa não existe para a validação. A confirmação grava as credenciais **da tentativa dona do código** (`user.ActivatePending`, numa única linha de UPDATE com `email_verified_at IS NULL`) e **consome todas as outras tentativas** do endereço. A linha de `users` continua nascendo no registro, mas só para **reservar o endereço** e sustentar o 403 `EMAIL_NOT_VERIFIED` do login — ela nunca ativa conta sozinha.
- **Por que fecha o ataque:** o navegador da vítima só tem **o token dela**. O código do atacante até chega à caixa da vítima, mas é inútil na mão dela; e o atacante tem o token dele, mas nunca vê o código, que foi para a caixa alheia. Nenhum dos dois fecha o par. E, como nenhuma tentativa destrói a alheia, a defesa **não** custa negação de cadastro.
- **Recuperação:** perder o token nunca trava ninguém — e a recuperação é **refazer o cadastro**, não o reenvio. `POST /auth/register` de novo sempre funciona, nunca é bloqueado por terceiro e sempre devolve um token amarrado às credenciais informadas. `POST /auth/resend-code` **exige** o token (rotaciona o código daquela tentativa, preservando-o); **sem** o token a resposta é o mesmo 202 do grupo B, mas **nada é emitido**.
- **Revisão de 09/09/2026 (achado ALTA-1):** ~~sem o token, o reenvio agia quando o endereço tinha exatamente uma tentativa viva~~ — esse caminho foi **removido**. A inferência "existe uma única tentativa viva, logo ela é de quem está pedindo" é falsa: o pedido carrega só um e-mail, e o atacante fabrica a condição sozinho, bastando que a tentativa da vítima tenha expirado e a dele esteja viva. A sucessora emitida herdava as credenciais **dele** e o token dela ia para a **vítima**, que ativava a conta com a senha do atacante ao usar o código da própria caixa. Não há conserto dentro do caminho: quem pede reenvio **não fornece credenciais**, então qualquer código emitido para ele herda as de outra pessoa.
- **Revisão de 09/09/2026 (achado ALTA-2) — só vale o código que foi EMITIDO:** a tentativa é gravada com código mesmo quando o cooldown ou a cota seguram a mensagem (é o que preserva o token de quem pediu), e `code_issued_at` fica **NULO** nesse estado. Como `register` não tem teto por endereço — de propósito, senão vira *lockout* por procuração — cada cadastro criava um código novo e **chutável sem gastar mensagem**, e a cota de mensagens/h por endereço (10/h desde 09/09/2026) deixava de limitar quantos códigos existem para adivinhar (5 palpites × 5 cadastros/h por IP, escalando com o número de IPs, tendo como prêmio uma conta **verificada** num endereço que o atacante nunca leu). Hoje `code_issued_at IS NOT NULL` entra no `WHERE` de `LiveByToken` **e** é reconferido no serviço: código que nunca saiu por e-mail não existe para a validação. A sentinela é **NULL**, e não o zero de `time.Time`, porque o zero não é portátil — o MySQL o recusa com erro 1292 (`NO_ZERO_DATE`), o que fazia a tentativa não nascer naquele dialeto. Quem ficou sem mensagem recupera pelo reenvio **com** o token, que gasta a cota e volta a ser contabilizado por ela.
- **Revisão de 09/09/2026 (achado BAIXA-3):** a reemissão disparada pelo login não verificado passa a exigir que a senha recém-provada seja a **da tentativa** a ser rotacionada. A linha de `users` guarda o hash de quem cadastrou primeiro, que pode ser um terceiro; sem essa amarração ele rotacionava a tentativa da vítima, matando o código que ela tinha na mão e gastando a cota dela.
- **Consequências:** o contrato de `register`, `resend-code` e `verify-email` muda (campo `registrationToken`), e o frontend precisa guardar o token entre as duas telas do cadastro. `verification_codes` fica sendo usado só por `password_reset`. A regra da §1.1 "código novo invalida os anteriores" passa a valer **por tentativa** — o que preserva a defesa contra força bruta, porque sem o token nenhum código é sequer procurado. O expurgo do janitor ganha as tentativas, com uma carência de um TTL depois da expiração para que quem queimou as 5 tentativas ainda consiga pedir outro código.

### ADR-015 — Tipos TypeScript gerados do OpenAPI; Go continua manual (12/09/2026)
- **Contexto:** o ADR-011 adiou o oapi-codegen e fixou dois gatilhos de reversão: **ultrapassar 25 endpoints** ou **a primeira geração de tipos TS**. O domínio financeiro (PLANOS.md §7) adiciona ~35 rotas e ~25 schemas, então os dois gatilhos disparam juntos. Decisão do usuário em 12/09/2026 (PLANOS.md D1).
- **Decisão:** a spec `backend/api/openapi.yaml` passa a **gerar os tipos TypeScript do frontend** (`frontend/src/api/schema.gen.ts`), que é o lado onde a duplicação seria de ~25 schemas escritos duas vezes. Os **tipos e handlers Go continuam manuais**: os handlers de autenticação têm comportamento deliberadamente não uniforme e crítico à segurança (ADR-011), e reescrevê-los para caber num gerador troca risco real por uniformidade cosmética.
- **Como se sustenta:** o arquivo gerado é **versionado** e checado no CI (`npm run api:check` falha se a spec e o arquivo divergirem), e `cmd/api/routes_test.go` continua garantindo `(método, path)`. Aderência de *schema* passa a ser garantida **de um lado só** (TS) — no Go segue por revisão humana, e é uma consequência aceita, não um esquecimento.
- **Consequências:** o frontend nunca inventa um campo que a API não tem, e renomear um campo na spec quebra o `tsc` em vez de virar `undefined` em produção. O ADR-011 fica **encerrado** quanto ao adiamento do gerador no frontend e **mantido** quanto ao Go.

### ADR-016 — Transferência entre contas como par de lançamentos (12/09/2026)
- **Contexto:** PLANOS.md D2, confirmado pelo usuário em 12/09/2026. As duas consultas mais frequentes do app são "extrato da conta" e "saldo da conta".
- **Decisão:** transferir cria **dois lançamentos** (`transfer_out` na origem, `transfer_in` no destino) com o mesmo `transfer_group_id`, sempre dentro do `UnitOfWork`. A alternativa (uma linha com `account_id` + `counterpart_account_id`) foi recusada: toda consulta por conta viraria `OR`, o saldo precisaria de `CASE` e o índice `(household_id, account_id, occurred_on)` deixaria de servir.
- **Invariantes:** transferência **nunca** tem `category_id`, **nunca** entra em receita/despesa de relatório e **nunca** consome orçamento; editar ou excluir age no **par inteiro**, identificado pelo `transfer_group_id`; meia transferência não existe porque a escrita é transacional (não há FK física — ADR-013).
- **Consequências:** extrato e saldo são soma direta e indexada, portáteis nos quatro dialetos. O preço é que a integridade do par é responsabilidade do código Go, o que vira item fixo de revisão de segurança e um teste de propriedade (soma de saldos estável após sequência aleatória de operações).

### ADR-017 — Saldo derivado e categoria com exatamente dois níveis (12/09/2026)
- **Contexto:** PLANOS.md D3 e D4, confirmados em 12/09/2026.
- **Decisão (a) saldo:** o saldo de uma conta é **sempre derivado** — `opening_balance_cents` + soma indexada dos lançamentos — e **nunca** uma coluna materializada. Coluna de saldo é a fonte clássica de saldo errado: basta um caminho de escrita esquecido para corromper o número, e o erro é silencioso. Numa casa (ordem de 10 mil lançamentos/ano) a soma é irrelevante em custo. Se um dia doer, entra snapshot mensal como **cache**, com a soma continuando a ser a verdade.
- **Decisão (b) categoria:** profundidade **exatamente 2** (grupo → subcategoria). Profundidade arbitrária exigiria CTE recursiva, cujo suporte e sintaxe variam entre os quatro dialetos — é precisamente o tipo de construção que quebra o requisito multi-banco. O `kind` (`income`/`expense`) é definido no nível 1 e **herdado**; filho não muda de `kind` nem vira raiz de outra árvore.
- **Consequências:** toda consulta de categoria é plana (`parent_id IS NULL` ou `parent_id IN (...)`), e o relatório soma o filho no pai com um único `GROUP BY`. Um pedido futuro de terceiro nível exige ADR próprio com a estratégia por dialeto resolvida antes.

### ADR-018 — Ocorrência de conta fixa: projeção virtual + tabela de exceções (12/09/2026)
- **Contexto:** PLANOS.md D7, confirmado em 12/09/2026. A alternativa era materializar 12 meses por job.
- **Decisão:** `recurring_bills` guarda a **regra**; as ocorrências mensais são **projetadas na leitura** e só existem em `bill_occurrences` quando houve um **fato** (pagou ou pulou). O status deriva, no fuso da casa: linha `paid` → pago · linha `skipped` → pulado · sem linha e vencimento < hoje → **atrasado** · sem linha e vencimento ≥ hoje → **pendente**. A ocorrência virtual é identificada na API por `billId + competenceMonth`, **nunca** por um id sintético que não existe no banco.
- **Por que não materializar:** job é mais uma peça para falhar, regra alterada deixa lixo materializado e a janela é sempre finita (o usuário rola para o 13º mês e não há nada lá).
- **Idempotência:** `UNIQUE(bill_id, competence_month)` é o que torna "pagar" idempotente — dois toques em conexão ruim geram **um** lançamento (§4.6 e S9 do PLANOS.md). As colunas do índice são obrigatórias, evitando a armadilha P3 (MSSQL trata NULLs como iguais em índice único).
- **Limitação aceita e documentada:** mudar o valor da regra muda o valor *esperado* dos meses passados **ainda não pagos** — o passado **pago** é imutável porque virou transação real. Mitigação, só se incomodar: versionar a regra por `starts_on`/`ends_on`.

### ADR-019 — Fuso na casa, BRL fixo, competência = caixa e fatura de cartão fora do v1 (12/09/2026)
> ⚠️ **As alíneas (c) e (d) foram SUPERADAS pelo ADR-023 em 16/09/2026.** As alíneas (a) fuso e (b) moeda continuam valendo integralmente.
- **Contexto:** PLANOS.md D6 e D9, confirmados em 12/09/2026.
- **Decisão (a) fuso:** `households.timezone` (default `America/Sao_Paulo`) é **regra de negócio, não formatação** — é ele que decide se uma conta está atrasada. "Hoje" e as bordas do mês são calculados no fuso da casa, nunca no do servidor nem no do navegador, num **único lugar** do domínio, testado com o processo em UTC **e** em `America/Sao_Paulo`.
- **Decisão (b) moeda:** `households.currency` existe com `BRL` fixo no v1. Nenhuma conversão, nenhum símbolo hardcoded na UI. A coluna nasce agora para que multimoeda não exija mudança destrutiva depois (o `AutoMigrate` não renomeia — ADR-008).
- ~~**Decisão (c) fatura de cartão: FORA do v1.**~~ **(SUPERADA pelo ADR-023.)** Fatura de verdade traz fechamento, vencimento, competência ≠ caixa, pagamento parcial e estorno — sozinha é do tamanho de uma fase. No v1 o cartão é uma conta como as outras (saldo negativo = dívida) e `accounts.kind` já prevê `credit_card` como rótulo. **Consequência aceita:** quem paga tudo no cartão vê o gasto na data da compra, não na data da fatura.
- ~~**Decisão (d) competência = caixa:**~~ **(SUPERADA pelo ADR-023.)** o mês de um lançamento é o do `occurred_on`. Quando a fatura entrar, entra como **coluna nova** (`transactions.competence_month`) e tabelas novas — o `AutoMigrate` faz isso sem quebrar.

### ADR-020 — Orçamento sem rollover, com cópia explícita do mês anterior (12/09/2026)
- **Contexto:** PLANOS.md D8, confirmado em 12/09/2026.
- **Decisão:** sobra de orçamento **não** vira crédito no mês seguinte no v1. Rollover dobra a complexidade de cálculo (o limite efetivo passa a depender de toda a cadeia de meses anteriores) e é minoria do uso doméstico. Em troca, `POST /budgets/copy-from-previous` copia todos os limites do mês anterior — **ação explícita, nunca automática**, e **idempotente por mês destino**.
- **Persistência:** o upsert é por `SELECT` + `INSERT`/`UPDATE` **dentro de transação**, não por sintaxe dialetal (`ON CONFLICT`, `ON DUPLICATE KEY`, `MERGE`) — armadilha P8. A unicidade é `(household_id, category_id, year_month)`, todas colunas obrigatórias (P3).
- **Consequências:** o cálculo de "gasto do mês" é um `GROUP BY year_month` sem histórico acumulado. Orçamento em categoria-grupo compara com a soma do grupo inteiro (pai + filhos). Reabrir rollover exige ADR próprio.

### ADR-021 — Gráficos em SVG próprio, sem biblioteca de visualização (12/09/2026)
- **Contexto:** PLANOS.md D11, confirmado em 12/09/2026. `docs/DESIGN.md` proíbe bibliotecas de componentes; uma biblioteca de gráficos é uma biblioteca de componentes com outro nome, e traz estética alheia junto (paleta, tipografia, animação, tooltip).
- **Decisão:** os gráficos do v1 (`BarChart` de evolução mensal, `DonutChart` por categoria, `LineChart` de evolução) são **SVG escrito para este projeto**, guiado pela skill `dataviz` e usando os mesmos tokens OKLCH do resto da UI. Nenhuma dependência de runtime é adicionada.

- **Consequências:** três componentes a escrever e testar na E6, contra zero dependências e identidade visual coerente. Se aparecer necessidade real de gráfico interativo complexo (zoom, brush, pan), a decisão reabre com ADR próprio — o gatilho é necessidade demonstrada, não conveniência.

### ADR-022 — Playwright cobre o navegador de verdade; Vitest fica em jsdom (12/09/2026)
- **Contexto:** o ADR-007 previu "Vitest 4 com **Browser Mode** para componentes", e a Fase 3 do ROADMAP ficou marcada `[~]` justamente porque os testes de componente rodam em jsdom. Na E0 o Playwright entrou em uso, com a suíte de autenticação passando contra a API Go real.
- **Decisão:** manter **Vitest + jsdom** para teste de componente e usar **Playwright** como a única camada que roda em navegador de verdade. O Browser Mode sai do plano; o ADR-007 fica revisto nesse ponto.
- **Por quê:** as duas ferramentas resolveriam o mesmo problema — comportamento que só existe num motor real. Manter as duas significa dois runners, dois conjuntos de seletores e duas suítes para manter em dia, e a que sobreviveria seria a que roda o fluxo inteiro, não a que monta um componente isolado num navegador. Entre elas, o Playwright cobre estritamente mais: ele exercita cookie `HttpOnly` de verdade, `SameSite`, checagem de `Origin` e o código de 6 dígitos que só existe porque o servidor o gerou.
- **O buraco que isso deixa, e como ele é tapado:** jsdom não implementa a Popover API (verificado em 12/09/2026 — sem `showPopover`, sem a propriedade `popover`, e `:popover-open` nunca casa), então um painel nativo ficaria invisível no teste de componente. A resposta **não** foi trocar o elemento nativo por um menu escrito à mão para agradar a ferramenta — `docs/DESIGN.md` manda usar o nativo primeiro, e ele é quem dá light dismiss, ESC e devolução de foco. A resposta foi um polyfill de teste em `frontend/src/test/popover-polyfill.ts`, que reproduz o comportamento observável e declara no cabeçalho o que **não** reproduz (top layer, empilhamento e gerenciamento de foco do navegador). Essas três coisas se verificam no Playwright.
- **Consequências:** um runner a menos para manter. Todo componente que dependa de comportamento de navegador — `Dialog` na E1, `ConfirmDialog` na E3 — nasce com teste de componente em jsdom **e** com um caminho coberto no E2E; o polyfill cresce junto se aparecer uma API que o jsdom ainda não tem.

### ADR-023 — Fatura de cartão de crédito: competência separada de caixa (16/09/2026) — ❌ supera o ADR-019(c) e o ADR-019(d)

- **Contexto:** o ADR-019(c) decidiu, em 12/09/2026, que fatura ficava fora do v1 e que `credit_card` era só rótulo, com a consequência aceita de "quem paga tudo no cartão vê o gasto na data da compra". Em 16/09/2026 o usuário reverteu: a importação de fatura entra na E2, e sem o conceito de fatura ela não tem onde pousar. O risco R1 do `PLANOS.md` ("cartão volta pela janela") se materializou — por decisão explícita, não por erosão de escopo.
- **Decisão (a) fatura é entidade:** `card_statements (household_id, account_id, competence_month, closing_date, due_date)` com `UNIQUE (household_id, account_id, competence_month)` — colunas todas obrigatórias, sem índice parcial (armadilhas P3/P4). É esse índice que torna "importar a mesma fatura duas vezes" uma operação idempotente, que reutiliza a fatura em vez de criar outra.
- **Decisão (b) competência ≠ caixa:** `transactions` ganha `competence_month CHAR(7) NOT NULL` — **sempre preenchido**, igual ao `year_month` fora de fatura e igual ao mês da fatura dentro dela — e `statement_id` anulável. A competência de uma fatura é o **mês do vencimento**, não o do fechamento: a fatura que fecha em 05/09 e vence em 13/09 é "a fatura de setembro" para o emissor e para o usuário, e é assim que o app a chama.
- **Decisão (c) "mês" no app inteiro é competência.** Listagem, painel, orçamento e relatório agregam por `competence_month`. Caixa (`year_month`) continua gravado e disponível, mas nenhuma tela do v1 o usa. Um conceito de mês, decidido aqui, para que E4–E6 não redecidam cada uma para o seu lado.
- **Decisão (d) o saldo derivado do cartão NÃO muda.** O ADR-017 continua inteiro: `balanceCents` do cartão é `opening_balance_cents` + soma de **todos** os lançamentos da conta — ou seja, a dívida corrente, negativa —, sem olhar competência. A fatura acrescenta números derivados **próprios**: `totalCents` (Σ das linhas com aquele `statement_id`), `paidCents` (Σ de `transfer_in` com aquele `statement_id`) e `status` (`paga` · `vencida` · `em_aberto`, no fuso da casa). **Nenhum deles é coluna.** Pagar a fatura é **transferência** da conta corrente para a conta do cartão (ADR-016), e é ela que traz a dívida de volta a zero.
- **Consequências:** o gasto do cartão passa a aparecer no mês da fatura, que é o que a pessoa espera, sem que o saldo deixe de ser caixa. O preço é uma coluna a mais escrita em toda linha e a regra "quem não registrar o pagamento como transferência vê a dívida do cartão crescer para sempre" — que a interface tem de **dizer em português**, não deixar a pessoa descobrir sozinha. Estorno continua fora (crédito na fatura vira receita — spec 0004 §2.4 D4) e parcelamento continua no backlog.

### ADR-024 — Importação de extratos e faturas: plugin por (instituição × documento), duas fases com staging, ZIP com senha sem dependência nova (16/09/2026)

- **Contexto:** decisão do usuário, em 16/09/2026, de importar extrato e fatura de C6 e Nubank. O `PLANOS.md` §1.3 listava "importação de OFX/extrato bancário" como **não-objetivo** do v1 e o §14 a colocava no backlog; a decisão a traz para a E2, e o §1.3 fica corrigido. O C6 entrega ZIP cifrado; o Nubank, CSV solto — e os dois arquivos do Nubank usam convenções de sinal **opostas**.
- **Decisão (a) parser é plugin, e a escolha é por detecção:** um `Parser` por par (instituição × tipo de documento), registrado num registro central e escolhido por **assinatura de cabeçalho**, com separador sniffado entre `,`, `;` e TAB. Zero candidatos → `IMPORT_FORMAT_UNKNOWN`; dois ou mais → `IMPORT_FORMAT_AMBIGUOUS`, e o cliente desempata com um `format` de allowlist. **Nunca "o primeiro que casou".** A `institution` da conta (coluna nova, allowlist `c6` · `nubank` · `other`) **não escolhe** o parser: ela é trava de consistência, junto com a trava mais forte — fatura só entra em conta `credit_card`, extrato só entra fora dela.
- **Decisão (b) convenção de sinal e formato numérico são DECLARADOS pelo parser**, nunca inferidos do conteúdo, e cada parser tem teste-ouro contra amostra real anonimizada. Um parser que infira sinal inverte a fatura inteira no dia em que o banco mudar o arquivo.
- **Decisão (c) duas fases com staging no banco:** `POST /imports` analisa e grava `import_batches` + `import_rows` (TTL de **24 h**); `GET /imports/{id}` pagina a revisão; `POST /imports/{id}/confirm` manda **só as exceções** ao default e é **idempotente** por transição condicional de status dentro do `UnitOfWork`; as linhas de staging são apagadas fisicamente no commit e o lote sobrevive como contadores. O desenho sem estado (o cliente devolve as linhas no confirm) foi recusado porque dissolve a garantia de que o que entrou foi o que o arquivo dizia; cache em memória foi recusado por não sobreviver a deploy nem a duas instâncias.
- **Decisão (d) ZIP cifrado sem dependência nova:** verificado em 16/09/2026 contra os arquivos reais do C6 — a cifra é **ZipCrypto** (PKWARE tradicional: `method=8`, `ReaderVersion=20`, flags `0x0809`, sem campo extra `0x9901`), não AES do WinZip. A stdlib **não detecta** a cifra (`f.Open()` manda os bytes cifrados direto para o inflate e devolve `flate: corrupt input`), mas `f.OpenRaw()` entrega os bytes crus intactos. Implementamos ZipCrypto (~60 linhas) sobre `archive/zip` + `compress/flate` + `hash/crc32`, com **o CRC32 do conteúdo inflado como único veredito de senha correta** — o byte de verificação do cabeçalho de 12 bytes **não serve** aqui, porque com o bit 3 (data descriptor) ligado ele é o byte alto da hora DOS, e não o do CRC; comparar com `CRC>>24`, que é o que a maioria dos exemplos faz, recusaria todo arquivo do C6 **com a senha certa**. Forks como `yeka/zip` e `alexmullins/zip` foram recusados: são cópias abandonadas do `archive/zip` inteiro, e não se troca 60 linhas testáveis por um parser de formato binário de terceiro no caminho mais perigoso do sistema. AES (`method=99`) é recusado com erro explícito até existir arquivo real que o use.
- **Consequências:** um banco novo custa um arquivo de parser e uma amostra de teste, sem tocar no núcleo. Em troca, o projeto passa a ter **upload de arquivo** — superfície nova, coberta pela §5 da spec 0004 (bomba de descompressão, path traversal, limite de corpo por rota, senha só em memória, rate limit próprio) — e uma tabela de staging com dado financeiro, que morre em 24 h por construção.

### ADR-025 — Deduplicação em camadas: chave canônica + ordinal de ocorrência, com o índice único como árbitro (16/09/2026)

- **Contexto:** exigência explícita do usuário em 16/09/2026 — nenhuma linha repetida pode entrar por engano, porque um erro dele não pode virar problema na aplicação. A proposta inicial (hash do arquivo → chave natural → chave derivada → índice único) tem um **defeito fatal na terceira camada**: chave derivada de `(conta, data, valor, descrição)` **apaga compra legítima repetida** — dois cafés iguais no mesmo dia na mesma padaria são a mesma tupla e são dois gastos reais. Num app de dinheiro, **sumir com um lançamento é pior do que duplicar um**: a duplicata o usuário vê e apaga, a linha que sumiu ele descobre três meses depois conferindo o extrato.
- **Decisão (a) a unicidade é `(household_id, dedup_key, dedup_ordinal)`**, três colunas `NOT NULL`, índice único comum. Índice **parcial** foi descartado porque o MySQL não tem (P4); coluna **anulável** em índice único foi descartada porque o MSSQL trata NULLs como iguais (P3) e deixaria passar exatamente uma linha sem id por casa. Toda linha tem chave, inclusive a manual (`v1|man|<id>`) e a perna de transferência (`v1|pair|<grupo>|in`) — é isso que permite a coluna ser obrigatória.
- **Decisão (b) o ordinal é a enésima ocorrência da tupla NA CASA**, contado no banco (inclusive linhas *soft-deleted*) e atribuído **dentro da transação do commit**. Duas compras idênticas entram como `#1` e `#2`; reimportar o arquivo reproduz `#1` e `#2`, que colidem com os existentes e são as duas barradas. É o que resolve, com a mesma peça, o falso positivo da compra repetida **e** o caso do mesmo período repartido em dois arquivos.
- **Decisão (c) a chave é calculada sobre os valores canônicos do domínio** — `kind`, `amount_cents`, `occurred_on` e a `description_norm` **já sanitizada e já truncada em 140** —, nunca sobre o texto cru do arquivo. Se usasse o texto cru, a truncagem do armazenamento faria a reimportação gerar chave diferente da gravada, e o dedup simplesmente não funcionaria — erro fácil de cometer e invisível em teste pequeno. SHA-256 simples, **sem HMAC**: não é credencial, não há ganho para um atacante em colidir as próprias linhas, e um *pepper* rotacionado cegaria o dedup contra todo o passado em silêncio. O `v1` no início da string é a versão, e mudá-lo exige ADR — na prática, **o sanitizador de descrição é parte do contrato de deduplicação**.
- **Decisão (d) o hash do arquivo é AVISO, não bloqueio**, e é calculado sobre o **conteúdo normalizado** (pós-extração, sem BOM, com quebra de linha normalizada para LF). Sobre os bytes do arquivo enviado ele seria inútil: duas compactações do mesmo CSV diferem em timestamp, nível de compressão e vetor da cifra. Como bloqueio ele seria frouxo (um byte a mais deixa passar um arquivo 99% repetido) e rigoroso ao mesmo tempo (travaria quem reimporta de propósito para pegar 3 linhas novas).
- **Decisão (e) marcação fraca, fora do índice:** mesma conta, mesmo valor, data ±3 dias com descrição diferente, ou `external_id` já usado em **outra conta** da casa, produz `possivel_duplicado` — **barrado por default, liberável caso a caso**. Ela cobre o buraco que a chave derivada tem (descrição que o banco enriquece entre um download e outro: `DL*99 RIDE` virando `99 Tecnologia Ltda`) sem transformar heurística em bloqueio irreversível no banco.
- **Decisão (f) liberar uma linha cuja gêmea está *soft-deleted* RESTAURA a linha existente**, em vez de inserir outra. Sem isso, apagar um lançamento importado criaria um beco sem saída: o índice recusaria a reimportação para sempre e o usuário não teria saída nenhuma. A restauração altera `deleted_at` e `updated_at` e **nada mais**, é escopada pela casa e gera auditoria própria (`transaction.restored`). É exceção estreita e declarada ao `PLANOS.md` §4.4.
- **Consequências:** a garantia anti-duplicata passa a ser do **banco**, não da aplicação — dois confirms simultâneos colidem no índice único e o segundo reporta "linha bloqueada" em vez de duplicar. O preço é uma coluna de hash em toda linha, um ordinal a calcular na escrita, e a disciplina de nunca mexer no sanitizador sem ADR.

### ADR-026 — Categorização por palavras-chave determinística em Go, transferência interna detectada por palavra-chave de conta e `link` como ação de importação (17/09/2026)

- **Contexto:** a spec 0004 deixou duas dívidas declaradas: todo lançamento importado nasce **sem categoria** (D3) e toda transferência entre contas da casa entra como receita numa e despesa na outra, inflando os dois relatórios. A spec 0005 (aprovada em 17/09/2026) paga as duas com **palavras-chave** cadastradas pela pessoa em categoria e em conta. A tentação óbvia — um classificador com modelo de linguagem, ou uma biblioteca de *fuzzy matching* — foi recusada antes de nascer: dado financeiro exige que a mesma descrição produza **sempre** a mesma sugestão, que a pessoa consiga **explicar** por que a sugestão apareceu ("88% · supermercado"), e que nada saia da máquina.
- **Decisão (a) — o algoritmo é determinístico, fechado e vive num pacote folha.** `internal/textmatch` depende só de `internal/textnorm` e implementa **exatamente** a §3 da spec 0005: tokenização por não-letra/não-dígito com lista **fechada** de palavras vazias; regra 1 (palavra inteira, 100), regra 2 (maior substring comum ≥ 5 runas, `100 − 30·sobraMaior − 40·sobraMenor`, em aritmética **inteira** com arredondamento meio-para-cima), regra 3 (distância de edição OSA/Damerau-Levenshtein **exatamente 1** em palavras ≥ 6 runas, `100 − 100/len`); limiar **80** como constante nomeada; **empate → nenhuma sugestão**. Sem regex do usuário, sem pesos, sem dicionário de sinônimos e **sem lista de exceções no código**: o falso positivo conhecido (`imposto` ⊃ `posto`, 91) se resolve cadastrando `imposto` na categoria certa, porque a regra 1 vence a 2. A tabela de exemplos da spec é o teste de unidade, com a pontuação exata de cada linha.
- **Decisão (b) — desempenho por prefiltro de trigramas COM preenchimento e memorização por descrição normalizada.** As regras 2 e 3 só rodam para pares (palavra da descrição × palavra-chave) que compartilhem ao menos um trigrama da forma preenchida (`"  " + palavra + " "`). O preenchimento não é detalhe: sem ele, uma transposição central numa palavra de 6 runas (`abcdef` → `abdcef`) não compartilha trigrama nenhum e a regra 3 a perderia. O prefiltro é **otimização, nunca semântica** — um teste de propriedade garante que ele jamais exclui um par que as regras aceitariam. O resultado é memorizado por `description_norm` dentro de uma análise, porque extrato repete descrição.
- **Decisão (c) — a cola fica em `internal/classify`, não no pacote folha nem duplicada nos consumidores.** Carregar as palavras-chave da casa, descartar categoria/conta **arquivada ou excluída**, separar categoria por natureza (`income`/`expense`) e excluir a conta do lote da escolha de contraparte é regra de domínio que dois consumidores compartilham (importação e `auto-categorize`). Ela vive num pacote pequeno que depende de `category`, `account` e `textmatch`; os serviços de lançamento e de importação o recebem como dependência **posicional** — esquecer de ligá-lo é erro de compilação, não uma importação que confirma sem sugerir nada.
- **Decisão (d) — palavra-chave é tabela própria, com índice único portátil por casa e por tipo.** `category_keywords` e `account_keywords` carregam `household_id` repetido (o isolamento nunca depende de join), `keyword` (forma exibível) e `keyword_norm` (forma de comparação), com `UNIQUE (household_id, keyword_norm)` — colunas `NOT NULL`, sem índice parcial (P3/P4). JSON na categoria foi recusado porque a unicidade por casa precisa de índice e JSON não é consultável igual nos quatro dialetos. O mesmo texto pode existir numa categoria **e** numa conta (conjuntos independentes); a mesma palavra em duas categorias é 409 `KEYWORD_TAKEN` citando a dona — sempre da mesma casa. Sem FK física (ADR-013): excluir a categoria apaga as palavras no mesmo `UnitOfWork`; arquivar as mantém, mas elas saem da correspondência.
- **Decisão (e) — transferência interna é detectada por palavra-chave de OUTRA conta ativa, e "conta batendo vence categoria batendo".** Na análise da importação, linha que entra por default e cuja descrição bate (≥ 80) com a palavra-chave de outra conta vira `transferencia_interna`, com `suggestedCounterpartAccountId`; a **própria** conta do lote é excluída **antes** da escolha, para nunca esconder a outra num empate nem gerar transferência para si mesma. Linha `pagamento_de_fatura` mantém o status (a classificação do parser é mais específica) e só ganha a contraparte sugerida. Detecção **sem** palavra-chave (só por valor e data espelhados) é conciliação e fica fora, com spec própria.
- **Decisão (f) — a outra perna já existente vira `link`, e `link` escreve numa linha existente.** Quando o extrato de B chega depois de o extrato de A já ter criado o par, a linha espelhada em B encontra a perna existente (mesma conta do lote, contraparte igual à sugerida, mesmo valor, ±`DedupWindowDays`, viva, ainda não apontada por outra linha do lote) e vira `transferencia_ja_registrada`. A ação `link` **não cria movimento**: grava na perna existente `external_id`, `dedup_key`, `dedup_ordinal` e `import_batch_id` desta linha, para a reimportação de B cair em `duplicado_exato`. É o **vetor novo** desta entrega: a perna vem **exclusivamente** do `match_transaction_id` gravado pela análise (o corpo do confirm não tem esse campo, e mandá-lo é 400), e é reconferida no commit por casa **e** conta do lote. Perna excluída entre a análise e o confirm → linha bloqueada; perna fora da casa ou incoerente (banco adulterado) → o lote **inteiro** falha, nada parcial.
- **Decisão (g) — contadores do lote viram colunas; o `footprint` deixa de contar pares.** `import_batches` ganha `linked_count` e `transfer_pairs_count` ao lado dos contadores que já são coluna. Derivar "pares criados" de `import_batch_id` deixou de ser possível: o `link` move o `import_batch_id` de uma perna para o lote que a vinculou, e a derivação passaria a mentir para os dois lotes. `ImportBatchFootprint` continua servindo só o `statementId`.
- **Decisão (h) — `auto-categorize` é uma escrita condicional em massa, com prévia obrigatória e recálculo no servidor.** `POST /transactions/auto-categorize` com `dryRun: true` devolve a prévia; com `dryRun: false` **recalcula** (nunca confia na prévia) e escreve com `UPDATE ... WHERE category_id IS NULL AND kind IN (income, expense) AND deleted_at IS NULL`, por categoria e em fatias — o número devolvido é o de linhas **afetadas**. Idempotente por construção. Uma entrada de auditoria por execução real (`transaction.auto_categorized`, entidade `transaction_month`, id = o mês): o `audit_log` não tem campo de detalhe por decisão registrada no pacote `audit`, então as contagens vão na resposta e no log estruturado, nunca a descrição.
- **Consequências:** a pessoa cadastra o nome do estabelecimento uma vez e a categoria vem pré-selecionada na próxima importação; a transferência entre as próprias contas deixa de inflar receita e despesa; `GET /transfers` e a tela `/transferencias` mostram cada par **uma vez**, com totais por sentido, líquido e saldo no fim do mês somados no servidor. O preço: duas tabelas novas, sete colunas novas, um pacote folha com quatro algoritmos de ~40 linhas testados por tabela, e a disciplina de que **nenhuma** exceção entra no código — quem quiser que `imposto` vença `posto` cadastra `imposto`. Reabrir para regra por valor/data, regex ou sinônimos exige ADR próprio.

### ADR-027 — Relatórios em pacote próprio `internal/report` (somente leitura) e percentual em pontos-base apurado no servidor (17/09/2026)

- **Contexto:** o usuário pediu, antes de E3–E5, a fatia "gastos por categoria" da E6 (`PLANOS.md` §7.5: `GET /reports/by-category?month&kind`, "soma o grupo com os filhos"). Era preciso decidir onde o relatório vive, como a árvore de dois níveis (ADR-017b) é dobrada sem CTE, como "Sem categoria" aparece e como o percentual trafega sem `float` (ADR-003, `PLANOS.md` §4.1).
- **Decisão (a) — pacote `internal/report`, leitura pura.** Relatório é consumidor de três domínios (lançamento, categoria e, na E6, conta) e não pertence a nenhum deles; colocá-lo em `transaction` faria aquele serviço conhecer a árvore de categorias e crescer sem fim. `report` declara **interfaces no consumidor** (`report.Ledger`, `report.Categories`), implementadas pelos repositórios já existentes em `gormstore` (`TransactionRepository` ganha `SumByCategory`; `CategoryRepository.List` já serve). Nenhuma escrita, nenhuma auditoria, nenhum `UnitOfWork`. Depende de `transaction` (constantes de `kind`, `ParseMonth`) e de `category` (tipo e teto por casa); nunca de `platform`.
- **Decisão (b) — agregação no banco, dobra em Go.** Uma consulta `GROUP BY category_id` sobre a janela `(household_id, competence_month, kind, deleted_at IS NULL)` — SQL ANSI igual nos quatro dialetos, servida por `ix_transactions_competence`; `NULL` agrupa numa linha só em todos eles. A saída é limitada pela taxonomia (≤ `category.MaxPerHousehold` + 1 linhas), não pelo volume de lançamentos — é o teto de S6 sem `LIMIT` em `GROUP BY` (que seria não determinístico). A dobra folha→grupo, o "lançado diretamente no grupo" (`direct*`), a ordenação (valor desc, contagem desc, nome) e o balde **explícito** "Sem categoria" (`categoryId: null`, nunca omitido) acontecem no serviço, sobre a lista plana de categorias da casa **incluindo arquivadas** (arquivada continua no relatório — `PLANOS.md` §4.4).
- **Decisão (c) — percentual é `shareBp` inteiro (0..10000), apurado no servidor.** Método do **maior resto em dois níveis**: primeiro 10000 pontos-base entre os grupos (Σ = 10000 exato); depois a fatia de cada grupo entre as suas partes (subcategorias + direto), de modo que `grupo.shareBp == directShareBp + Σ filhos.shareBp` exato. A única multiplicação (`centavos × 10000`) é feita em **128 bits** com `math/bits.Mul64`/`Div64` — nunca estoura `int64` e não usa `float`. O cliente **não calcula** percentual: só formata `shareBp`. Mesma razão do `summary` de `GET /transactions`: dois lugares calculando o mesmo número divergem.
- **Decisão (d) — gráfico é rosca SVG própria (ADR-021) com rampa monocromática por tokens.** Categoria **não ganha cor** no modelo: cor cromática é reservada a estado financeiro (`docs/DESIGN.md`, princípio 3), e uma paleta categórica de 12 matizes é exatamente a "cara de dashboard genérico" que o projeto rejeita. A identidade da fatia vem de posição + rótulo + número na tabela; a rampa sai de `color-mix` sobre os tokens, e a tabela abaixo é a fonte — o SVG é `aria-hidden`.
- **Decisão (e) — rota `/relatorios/categorias` e item "Relatórios" na navegação.** A URL do relatório por categoria nasce definitiva; a E6 acrescenta os demais sob `/relatorios/*` com sub-navegação, sem mover esta. Nenhum item ou aba "em breve": item só nasce com tela que abre.
- **Decisão (f) — anomalia de dado no relatório: referência órfã falha ABERTA, taxonomia estourada falha FECHADA, e o aviso é um só por requisição (17/09/2026, revisão de segurança da E6a).** A regra em uma frase: *o relatório tolera — e avisa sobre — a referência que aponta para fora da taxonomia da casa, mas recusa a resposta inteira quando a própria taxonomia foi violada.* Um `category_id` que a casa não tem, ou uma folha cujo `parent_id` sumiu, é **referência órfã**: o dinheiro existe e tem para onde ir (o balde "Sem categoria"; a folha promovida a grupo), e sumir com ele em silêncio seria pior que mostrá-lo sem nome. Já mais de `category.MaxPerHousehold + 1` linhas na agregação é coisa diferente em natureza — o teto da própria casa foi rompido, o relatório não sabe mais o que é a taxonomia dela e qualquer saída seria invenção: **500 genérico**, com a contagem no log e nada mais. Os dois caminhos avisam no `slog`, mas **uma vez por requisição, agregado** (contagem por tipo de anomalia + amostra de no máximo 5 ids distintos): um registro por linha anômala daria até 200 por requisição e, dentro do limite de 100 req/min, viraria amplificação de log a custo zero para quem já tem token válido. O aviso nunca leva nome de categoria, centavos nem a consulta. Pela mesma razão, toda soma publicada pelo relatório passa por `somaSegura`, que **verifica** (não confia) que as parcelas são não negativas antes de conferir o estouro de `int64`.
- **Consequências:** o primeiro relatório entra sem migração, sem índice novo e sem dependência nova; E6 reutiliza o pacote, o `DonutChart` e o mecanismo de `shareBp`. O preço é um pacote a mais e a disciplina de que **todo número derivado de dinheiro (percentual incluído) nasce no servidor** — o frontend formata, nunca calcula. A chave de query do relatório no frontend fica sob o prefixo `['transactions', …]` para ser invalidada por toda mutação que já invalida lançamentos, sem edição cruzada entre features.

### ADR-028 — Reprocessar transferências sobre lançamentos já gravados: só pareia, nunca inventa perna; palavra-chave de conta com dupla semântica (17/09/2026)

- **Contexto:** os extratos de C6 e Nubank do banco de desenvolvimento foram importados **antes** de as palavras-chave de conta existirem. Os Pix entre as duas contas entraram como `expense` numa e `income` na outra; `/transferencias` ficou vazia e `/lancamentos` inflou receita e despesa em R$ 8.000 no mês. Reimportar cai em `duplicado_exato` (ADR-025 fazendo o seu trabalho) e **não existia nenhum caminho para reclassificar o que já está gravado**. Além disso, a semântica do ADR-026(e) — "palavra-chave de **outra** conta" — não cobre o Pix entre contas próprias, que é o caso mais comum da casa: "Pix enviado - BRUNO RIBEIRO BLANCK" não nomeia o banco de destino, e a pessoa, naturalmente, cadastra a palavra na conta onde o texto **aparece** — justamente a que a análise exclui. Spec 0005 §13 (emenda aprovada pelo usuário em 17/09/2026). O ADR-016 é reafirmado: transferência é um tipo de lançamento à parte e **nunca** entra em receita, despesa ou total.
- **Decisão (a) — reprocessamento só PAREIA, nunca inventa perna.** `POST /transfers/detect` converte **pares já gravados** (`expense` numa conta + `income` em outra, mesmo valor, `occurred_on` a ±`DedupWindowDays`) em `transfer_out`/`transfer_in` com um `transfer_group_id` novo. Candidata **sem espelho** fica como está e aparece na prévia com `reason: no_mirror`. É a diferença deliberada em relação ao `transfer` da importação (ADR-026e/f), onde a outra perna comprovadamente ainda não existe: criar perna sintética aqui duplicaria dinheiro na próxima importação da outra conta — a linha espelhada entraria como receita ao lado da perna inventada, e o dedup (que compara `kind`, valor, data e descrição da **própria** conta) não teria como barrá-la. A orientação para a pessoa é "importe o extrato da outra conta e reprocesse".
- **Decisão (b) — a palavra-chave de conta tem DUAS semânticas, decididas pela conta dona da melhor pontuação.** `classify.Set` ganha `MatchAccount(descriptionNorm)`: a escolha da §3 sobre **todas** as contas ativas da casa, **sem** exclusão — e não `SuggestCounterpart` com exclusão vazia, porque o nome daquele método promete "contraparte" e o chamador dependeria de um truque de string vazia para obter outra semântica. O serviço compara a dona com a conta da linha: **outra conta `K`** → contraparte conhecida (semântica do ADR-026e): o espelho `M` tem de estar em `K`, e bater com palavra não é exigido dele; **a própria conta** → marcador "isto é transferência entre as minhas contas", contraparte desconhecida: `M` tem de estar em outra conta ativa **e** qualificar-se também (a melhor pontuação de `M` aponta para a própria conta de `M` ou para a conta de `T`). Sem essa segunda exigência, "Pix enviado a mim mesmo" casaria com qualquer receita de mesmo valor na vizinhança — o falso positivo que a §2.2 da spec recusou. **Empate** na pontuação máxima entre contas diferentes (inclusive entre a própria e outra) → **não é candidata**, pela mesma regra de sempre: ambíguo é pior que vazio, e a saída é cadastrar a palavra mais específica. A análise da **importação** continua com a semântica do ADR-026(e) — só outra conta, própria excluída antes da escolha; ensinar-lhe a dupla semântica fica no backlog (alínea g).
- **Decisão (c) — pareamento determinístico em Go, com a janela de espelhos derivada das candidatas.** Duas consultas, nenhuma por linha: as candidatas do mês de **competência** (`kind IN (income, expense)`, viva, sem grupo — `ix_transactions_competence`) e o **pool de espelhos** da casa inteira por `occurred_on` em `[min(occurred_on das candidatas) − 3, max(...) + 3]` (`ix_transactions_occurred`), porque a competência de `M` pode ser outra (linha de fatura). A janela sai do intervalo real das candidatas, e não das bordas do mês, porque uma candidata de fatura pode ter `occurred_on` fora do mês de competência — a janela pelas bordas do mês a deixaria sem espelho por construção. Balde por `(kind oposto, amount_cents)`; `T` percorrida em ordem `(occurred_on, id)`; entre várias `M` possíveis vence a que também se qualifica, depois a de menor distância em dias, depois menor `occurred_on`, depois menor `id`; `T` e `M` são **reivindicadas** e cada uma participa de um único par. Contas envolvidas precisam ser **ativas e distintas**; `T` e `M` nunca são a mesma linha. Puro e testado por tabela, como `pairExistingLegs` do importador — a mesma ideia, entre lançamentos vivos em vez de linha de arquivo × perna. O sentido do par vem do `kind`: a `expense` vira `transfer_out`, a `income` vira `transfer_in`.
- **Decisão (d) — `UPDATE` condicional, duas linhas afetadas por par, tudo ou nada, recálculo dentro da transação.** A confirmação (`dryRun: false`) **recalcula** tudo dentro de **uma** transação — nunca confia na prévia, como o ADR-026(h) — e converte cada par com `UPDATE ... SET kind = ?, transfer_group_id = ?, category_id = NULL, updated_at = ? WHERE household_id = ? AND id = ? AND deleted_at IS NULL AND transfer_group_id IS NULL AND kind = <esperado>`. Cada par tem de afetar **exatamente 2 linhas** (1 + 1); qualquer outro número desfaz a transação inteira e responde **409 `CONFLICT`** — código novo no conjunto fechado, porque mapeia para uma ação própria da tela: pedir a prévia de novo (D4 da spec 0003). O `kind` sempre muda, então o MySQL — que só conta mudança real — nunca devolve 0 por "nada mudou". **Nada mais muda**: valor, data, competência, descrição, `source`, `import_batch_id`, `external_id`, `dedup_key`, `dedup_ordinal` e `statement_id` ficam como estão — a reimportação do mesmo arquivo continua caindo em `duplicado_exato`, e o saldo das duas contas **não muda** (−X em despesa vira −X em saída; +X em receita vira +X em entrada — `SumByAccount` já trata os dois pares de `kind` com o mesmo sinal). Idempotente por construção: a segunda execução não encontra `income`/`expense` para os mesmos pares e responde `paired: 0`. A prévia não escreve nem audita.
- **Decisão (e) — auditoria uma vez por execução real.** `transaction.transfers_detected`, entidade `transaction_month`, id = o mês, gravada **dentro** da transação (se o rastro não couber, a conversão não vale) — a mesma decisão da emenda §10.5 e do ADR-026(h). Contagens (`paired`, `unpaired`) vão no `slog` e na resposta; descrição, valor e palavra-chave **nunca** vão para log nem auditoria.
- **Decisão (f) — tetos e cota próprios.** `MaxTransferDetectRows = 10.000` candidatas por mês e `MaxTransferMirrorRows = 20.000` linhas no pool de espelhos: acima é 422, **nunca** execução parcial (parear "os 10.000 primeiros" deixaria a pessoa sem saber quais ficaram de fora). Listas da prévia param em 500 cada; contagens sempre completas. Rate limit **por casa**, balde separado do `auto-categorize`, 60/h — cada uso gasta prévia + confirmação. O corpo **não tem ids**: o cliente não escolhe o que converter, a prévia é informativa.
- **Decisão (g) — o que fica no backlog (spec 0005 §13.6), declarado para não virar dívida invisível:** (1) ensinar a **análise da importação** a mesma dupla semântica — "palavra da própria conta" + espelho já gravado em outra conta, convertendo a linha existente em vez de criar perna; até lá a importação continua como no ADR-026(e) e o reprocessamento fecha o mês em um clique depois; (2) linha que espelha uma perna **sintética** já existente na própria conta (fatura importada com `transfer` antes do extrato) — o `link` cobre no momento da importação, fora dela fica para spec própria; (3) **desfazer** a conversão (voltar o par a receita/despesa).
- **Consequências:** a casa que importou tudo antes de cadastrar palavras-chave conserta o mês em dois cliques, sem reimportar e sem perder a proteção contra duplicata; `/transferencias` passa a listar os pares e o `summary` de `/lancamentos` deixa de contar dinheiro que só mudou de conta. O preço: dois métodos novos de leitura e um de escrita no repositório de lançamentos, um método novo no `classify.Set`, um código de erro novo (`CONFLICT`) e a disciplina de que **duas semânticas para a mesma palavra-chave existem só aqui** — a importação continua com uma, até o backlog (g.1) unificá-las com spec própria. Reabrir para pareamento sem palavra-chave (só valor e data) continua sendo conciliação e exige ADR próprio.

### ADR-029 — Investimento é NATUREZA DE CATEGORIA: sem tipo de lançamento novo, sem conta de carteira, sem coluna nova; e troca de natureza liberada dentro do mesmo lado do dinheiro (17/09/2026)

- **Contexto:** a casa investe e resgata pelo mesmo extrato com que paga o mercado. Hoje um aporte de R$ 2.000 entra como despesa comum, some dentro do relatório por categoria como se fosse gasto, e "quanto eu guardei este mês" só se responde somando à mão. A spec 0006 (aprovada pelo usuário em 17/09/2026, com as quatro decisões de desenho respondidas na entrevista) pede **controle de fluxo** — quanto entrou e saiu de investimento por mês — e **não** carteira: patrimônio, posição, rentabilidade, cotação, ativo e corretora continuam fora (`PLANOS.md` §1.3, corrigido na mesma data). As três alternativas óbvias foram recusadas antes de nascer. **Tipo de lançamento novo** (`investment_out`/`investment_in`): obrigaria saldo, extrato, deduplicação, fatura, transferência e todo `switch` de `kind` a aprender dois valores a mais — e o aporte continuaria sendo, no extrato, dinheiro que saiu da conta; ganharíamos um conceito e perderíamos a verdade do caixa. **Conta de carteira** com transferência (ADR-016): esconderia o aporte de todo relatório por construção e criaria um saldo que ninguém alimenta, porque o app não lê corretora. **Coluna `is_investment`** em `transactions`: seria um segundo eixo de classificação ao lado da categoria, mantido à mão linha por linha, que dessincroniza no primeiro mês.
- **Decisão (a) — a marcação é a NATUREZA DA CATEGORIA, e só a allowlist da aplicação cresce.** `categories.kind` ganha `investment` (aporte) e `redemption` (resgate) ao lado de `income` e `expense`. Mesmo cadastro, mesma árvore de exatamente dois níveis (ADR-017b), mesmas palavras-chave (ADR-026d), mesmo teto de 200 por casa, mesmo ciclo de arquivar e excluir. **Nenhuma tabela nova, nenhuma coluna nova, nenhum índice novo:** as duas palavras têm exatamente 10 caracteres e cabem no `varchar(10)` que já existe — o schema **não muda de versão** e o `AutoMigrate` não tem o que fazer. Os grupos "Investimentos" e "Resgates" entram em `DefaultGroups()`; como a semente é idempotente e roda no auto-reparo do login (`household.EnsureDefault`), as casas que já existem os recebem **sem migração de dados**. O preço, registrado: uma quinta natureza mais longa exigirá alargar a coluna — portátil nos quatro dialetos, mas migração.
- **Decisão (b) — o lançamento continua `income`/`expense`; o pareamento passa a ser por LADO DO DINHEIRO.** Despesa aceita categoria `expense` **ou** `investment`; receita aceita `income` **ou** `redemption`; transferência continua sem categoria nenhuma (ADR-016). Aporte é dinheiro que **sai** da conta e resgate é dinheiro que **entra** — é o que o extrato diz, e o saldo derivado (ADR-017) não muda uma linha. A regra do pareamento passa a existir **uma vez só**, no pacote `category`: hoje ela está escrita duas (`transaction.categoriaCombina` e `importer.categoriaCombinaComALinha`), e duas cópias de uma allowlist divergem — a segunda é sempre a esquecida.
- **Decisão (c) — trocar a natureza DENTRO do mesmo lado é permitido com a categoria EM USO; cruzar o lado continua travado.** `expense ↔ investment` e `income ↔ redemption` passam a ser aceitos mesmo com lançamentos pendurados e, quando o grupo tem subcategorias, **a troca desce para todas elas (ativas e arquivadas) na mesma transação** — a folha herda a natureza do grupo (ADR-017b), e folha sozinha continua `ErrKindLocked` pelo mesmo motivo de sempre. `expense ↔ income` continua recusado. **A assimetria não é conservadorismo:** dentro do mesmo lado, nenhum lançamento existente muda de sinal, de conta ou de saldo, e todos continuam válidos contra o pareamento da alínea (b) — a troca é de **rótulo de intenção**, não de fato financeiro. Cruzar o lado transformaria despesa registrada em receita, inverteria o resultado de meses fechados e deixaria **todo** lançamento da categoria em violação do pareamento no instante seguinte. Esta alínea é o que torna a entrega usável por quem já tem uma categoria "Investimentos" cheia de lançamentos: sem ela a única saída seria criar outra categoria e recategorizar à mão, e recategorização em massa do que **já tem** categoria está fora de escopo desde a spec 0005 §2.2. **Consequência declarada, não escondida:** os números de receita e despesa dos meses passados **mudam de valor no instante da troca** — ela é explícita, auditada com autor (`category.updated`) e reversível pelo mesmo caminho.
- **Decisão (d) — um predicado só, e o FLUXO vem do `kind` do LANÇAMENTO.** Tudo o que esta entrega soma, esconde ou marca responde à mesma pergunta: *"a categoria deste lançamento está no conjunto das naturezas de investimento da casa?"*. O conjunto sai de **uma** leitura da taxonomia (≤ 200 linhas, **arquivadas incluídas** — arquivar não desfaz a marcação do passado, `PLANOS.md` §4.4). Dentro dele, **aporte é o lançamento `expense` e resgate é o `income`**, nunca a natureza da categoria. Parece detalhe e não é: é o que garante que o que **sai** de `expenseCents` seja exatamente o que **entra** em `investedCents`, e que a tela de investimentos e a faixa do mês em `/lancamentos` não possam divergir nem diante de dado anômalo. Duas perguntas diferentes para o mesmo número é como se começa a ter dois números.
- **Decisão (e) — a exclusão vale em DUAS agregações, e em mais nenhum lugar.** Saem de `GET /reports/by-category` (dos totais e das linhas; o balde "Sem categoria" não muda) e de `incomeCents`/`expenseCents`/`netCents` do `summary` de `GET /transactions`, que ganha `investedCents` e `redeemedCents` **sempre presentes**. **Não mudam:** saldo de conta, extrato, listagem, `uncategorizedCount`, deduplicação, fatura de cartão, transferência e orçamento — nenhuma consulta de saldo olha a natureza da categoria. E a subtração **tem de aparecer na tela**: a faixa do mês diz "e R$ 2.000,00 investidos". Um total que encolhe sem explicação é mentira por omissão.
- **Decisão (f) — `IN ()` nunca é emitido; o curto-circuito é em Go.** Casa sem nenhuma categoria de investimento — o caso de **todas** as casas no dia da entrega — responde zeros, `items: []` e série de 12 meses zerada **sem consultar o banco**. `IN ()` é erro de sintaxe em três dos quatro dialetos e comporta-se como `1=0` no outro; a diferença entre "não há" e "a consulta quebrou" não pode depender do dialeto.
- **Decisão (g) — a correspondência por palavra-chave passa a ser por LADO DO DINHEIRO, em UMA passagem.** `classify.Set` continua com **dois** matchers de categoria, e não quatro: o de despesa carrega as palavras de `expense` **e** de `investment`; o de receita, as de `income` **e** de `redemption`. A assinatura de `SuggestCategory(kind, descriptionNorm)` não muda — e com isso a análise da importação (spec 0005 §4.2) e o `auto-categorize` ganham as naturezas novas **sem uma linha de código nova**. Dois matchers por lado, e não dois passes: o limiar 80, o desempate e a regra "empate → nenhuma sugestão" do ADR-026(a) só valem se a escolha for **uma**. Com dois passes, "CDB" (investimento, 88) e "Mercado" (despesa, 88) produziriam dois vencedores e alguém teria de inventar um critério entre passes — exatamente a ambiguidade que a regra existe para recusar.
- **Decisão (h) — `/investments` e `/investments/detect` são recursos próprios, dentro do domínio `transaction`.** Não um `kind` a mais em `/reports/by-category` (cujo parâmetro continua `income|expense` — o relatório de investimento é tela própria), não um filtro em `/transactions`, e **não** um pacote novo: o predicado da alínea (d) é o mesmo do `summary`, e só há uma forma de garantir que duas telas não divirjam sobre dinheiro, que é o número nascer no mesmo lugar. Ao `internal/report` cabe apenas **descartar** as linhas marcadas, com o mapa de categorias que ele já carrega (ADR-027b) — regra de uma linha, não relatório novo. `POST /investments/detect` é o desenho de sempre — prévia obrigatória, recálculo no servidor, escrita condicional, teto duro, auditoria uma vez por execução real (ADR-026h, ADR-028d) — com **uma diferença declarada**: a flag `overwriteCategorized`, a primeira escrita do projeto autorizada a **substituir categoria já escolhida**. Ela é opt-in, tem confirmação própria na tela, e a substituição é **fechada por allowlist dentro do `WHERE`**: só troca categoria de natureza `income`/`expense`, então nunca desfaz uma marcação de investimento — nem a de outra execução, nem a que a pessoa fez à mão.
- **Decisão (i) — a exclusão do relatório cria um jeito de esconder gasto, e isso é ACEITO com mitigação declarada.** Marcar uma despesa grande como investimento a faz sumir do relatório de despesas; numa casa com dois membros, isso é um vetor real, e a única honestidade possível é escrevê-lo aqui. Mitigação: o lançamento **continua visível** em `/lancamentos`, passa a aparecer em `/investimentos`, a soma que saiu do relatório **aparece nomeada** na faixa do mês, e toda troca de categoria e de natureza já é auditada com autor. Nenhuma mitigação adicional nesta entrega — e a decisão de não ter uma é do usuário, registrada na §6.5 da spec 0006.
- **Decisão (j) — a marcação entra na PROJEÇÃO, não no `GROUP BY` (ratificado em 18/09/2026, sobre a entrega do `arquiteto-dados`).** O plano da E7 pedia `GROUP BY kind, CASE WHEN category_id IN (…) …`. **Não é implementável sem SQL montado:** `gorm.DB.Group` recebe `string` e não aceita variáveis de bind (as colunas de `clause.GroupBy` são escritas com `Raw: true`, sem vars), então repetir a expressão como chave de agrupamento obrigaria a escrever os ids **no texto** do comando — injeção (docs/SEGURANCA.md §3), recusada pelo `TestSemSQLMontadoNoGormstore`. Agrupar pelo **alias** não é alternativa: MSSQL e PostgreSQL não agrupam por alias. A forma que vale é a condicional na projeção — `COALESCE(SUM(CASE WHEN category_id IN (?) THEN amount_cents ELSE 0 END), 0) AS marked_total` — com o `GROUP BY kind` intacto, e a receita/despesa exibida sendo `total − marked_total`. **Continua sendo uma consulta só, e é isso que importa:** a subtração acontece **dentro da linha agregada**, entre dois agregados das **mesmas** linhas — não entre duas leituras que uma escrita concorrente poderia separar, que era o risco que o plano existia para evitar. Com o conjunto vazio a coluna condicional **não entra na consulta**, e o SQL emitido volta a ser byte a byte o de antes da E7. Forma completa das cinco consultas e os cuidados de cada dialeto: `docs/BANCO-DE-DADOS.md`, "Schema v4 — sem mudança: naturezas de investimento".
- **Decisão (j.1) — `marked_total ≤ total` é VERIFICADO, não confiado.** A prova de que a subtração não produz despesa negativa depende de `amount_cents ≥ 0`, que é invariante do **caminho de escrita** e não do schema (não há `CHECK`, e criar um agora seria mudança destrutiva de uma coluna povoada). Uma única linha negativa — corrupção, ou um caminho de escrita futuro com defeito — publicaria `investedCents` negativo contra um contrato que declara `minimum: 0`, ou uma despesa maior que a real. Vale aqui a mesma disciplina que o `somaSegura` do `internal/report` passou a ter depois do achado B3: **verificar** que `0 ≤ marked_total ≤ total` por `kind` antes de publicar e, na violação, **falhar fechado** — erro genérico, uma linha de log com as contagens, nenhum número inventado na tela. Clampar em silêncio seria pior: esconderia a corrupção e ainda assim publicaria um total errado.
- **Decisão (j.2) — teto do filtro de categorias: falha ALTO no repositório e FECHADO na borda.** O conjunto de ids nunca é **fatiado** (fatiar uma agregação obrigaria a somar fatias de dinheiro; fatiar uma consulta paginada por cursor quebraria a página), então ele tem teto duro de 200 — o mesmo `category.MaxPerHousehold` — e acima disso é `transaction.ErrTooManyCategories`, antes de qualquer SQL. **Ele mapeia para 500 genérico, nunca para 4xx**, e isto precisa estar escrito porque o nome do erro convida ao engano: `ErrTooManyUncategorized` é 422 em `fields.month`, mas aquele conta **lançamentos** (que a pessoa pode dividir em dois meses) e este conta **categorias da própria casa**, que já têm teto próprio. Passar de 200 significa que o teto da taxonomia foi violado — é a situação do ADR-027(f), "taxonomia estourada falha FECHADA": o servidor não sabe mais o que é a taxonomia da casa e qualquer resposta seria invenção. Um 422 apontaria um campo que a pessoa não tem como corrigir naquele pedido. Log com a contagem, nunca com os ids.
- **Decisão (j.3) — o `UPDATE` do `overwriteCategorized` não tem a armadilha do MySQL.** `SetCategoryWhereCurrentIn` devolve linhas afetadas, e o MySQL conta **mudança real**; aqui `category_id` sempre muda de fato, porque a allowlist do `WHERE` só admite categoria de natureza `income`/`expense` e o valor gravado é sempre uma de **investimento** — origem e destino nunca coincidem. Mesma razão pela qual `SetCategoryWhereNull` (de `NULL` para um valor) e o `UPDATE` de conversão do ADR-028(d) (o `kind` sempre muda) estão livres dela. Registrado para não ser reinvestigado a cada revisão.
- **Consequências:** a casa passa a responder "quanto guardei este mês e no ano" sem planilha, sem que saldo, deduplicação ou fatura saibam que investimento existe, e sem nenhuma migração. O preço: dois valores a mais numa allowlist que atravessa contrato, banco, classificador e três telas; uma regra de pareamento que, se voltar a ser escrita em dois lugares, volta a divergir; e o fato de que os números de receita e despesa de **meses passados podem mudar** — de propósito, pela mão da pessoa, e só dentro do mesmo lado do dinheiro. Reabrir para patrimônio, posição ou rentabilidade exige ADR próprio: é carteira, não controle de fluxo, e traz cotação, ativo e corretora junto.
